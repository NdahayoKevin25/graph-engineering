# Reference Architecture

Analysis of the provided reference application (`reference-app/`, extracted from `Archive.zip`), which becomes the source of conventions for `graph-templates/`.

## 1. Existing architecture

A single-process Express REST API, layered `route → service → repository → database`, with TypeScript compiled to `dist/`. No frontend is included. The app implements one bounded feature end-to-end (authentication) and is explicitly documented as a starter to extend ("Add feature routes in `src/routes`, business logic in `src/services`, persistence helpers in `src/repository`").

Request flow: `app.ts` wires global middleware → mounts `routes/*Routes.ts` → route calls a `*Service` method directly (services are instantiated per-router, not injected) → service calls a `*Repository` method → repository runs Drizzle queries against `database` (Neon serverless Postgres over a WebSocket `Pool`).

## 2. Existing folder structure

```
src/
  app.ts                 Express app + middleware wiring + listen()
  config/                 database.ts, schema.ts, s3-client.ts, multer.config.ts
  middlewares/             authMiddleware.ts, errorMiddleware.ts
  migrations/              Drizzle-generated SQL + meta/ snapshots
  repository/              *.ts, one class per aggregate, `new Class()` exported or instantiated by services
  routes/                  express.Router() per feature, thin — no controller layer
  services/                business logic + request/response shaping, talks to Express Request/Response directly
  utils/                   helpers.ts (env/SECRETS, HttpStatusCodes enum), types.ts (DTOs)
neon.ts                   Neon branch-provisioned object storage config (declares the "media" bucket)
drizzle.config.ts         drizzle-kit config, reads DATABASE_URL
```

Notable: there is **no controller layer** — the route handler calls the service directly, and the service takes `(req, res)` rather than plain DTOs and returning data. There is also no DI container; every class is directly `new`'d where used.

## 3. Existing dependencies

- **Runtime**: `express`, `cors`, `helmet`, `morgan`, `cookie-parser`, `dotenv`
- **DB**: `@neondatabase/serverless` (Pool + `ws` WebSocket constructor), `drizzle-orm` (`neon-serverless` driver), `drizzle-kit` for migrations, `pg` (present but unused directly — Drizzle uses the Neon driver)
- **Storage**: `@aws-sdk/client-s3`, `@aws-sdk/s3-request-presigner`, `multer` (memory storage)
- **Auth**: `jsonwebtoken`, `bcrypt`, `email-validator`
- **Dev**: `typescript`, `ts-node`, `ts-node-dev`, `nodemon`
- **Build**: `tsc` (CommonJS, ES6 target, `strict: true`, `rootDir: src`, `outDir: dist`)
- Package manager: npm (`package-lock.json` present)

No test framework, no linter config, no Docker, no CI is present in the archive.

## 4. Existing database approach

- Neon serverless Postgres, accessed via `@neondatabase/serverless`'s `Pool` with `ws` as the WebSocket constructor (required for non-edge Node runtimes), wrapped by `drizzle-orm/neon-serverless`.
- Schema defined declaratively in `src/config/schema.ts` using `pgTable`/`pgEnum` — enums for `user_role`, `user_status`, `auth_token_type`; tables for `users`, `user_profiles` (1:1 split of auth vs. profile data), `auth_tokens` (single table for both email-verification and password-reset tokens, disambiguated by `type`, tokens stored as SHA-256 hashes not raw values).
- Migrations generated by `drizzle-kit generate` into `src/migrations/*.sql` + `meta/` snapshots, applied via `drizzle-kit migrate`. `drizzle.config.ts` reads `NEON_DATABASE_URL ?? DATABASE_URL`.
- Multi-row writes (user + profile) wrapped in `database.transaction(...)`.
- No repository-level pagination/filtering/sorting exists yet — only single-row lookups by email/id.
- `neon.ts` is a separate, non-Drizzle config file used by Neon's branch-provisioning tooling to declare additional branch-scoped resources (here, the private `media` object-storage bucket) — distinct from application runtime config.

## 5. Existing S3 implementation

- `src/config/s3-client.ts`: constructs one module-level `S3Client`, pointed at an S3-**compatible** endpoint (`AWS_ENDPOINT_URL_S3`, not implicit AWS default — this targets Neon Object Storage or any S3-compatible provider), `forcePathStyle: true`, fails fast if any of endpoint/region/access key/secret is missing.
- `src/config/multer.config.ts`: `multer.memoryStorage()` — files land in `req.file(s).buffer`, never touch disk, so they can be streamed straight into `PutObjectCommand`.
- `src/repository/FileUpload.ts` (singleton, exported instance not class): `uploadFileToS3` builds a collision-resistant key `uploads/${randomUUID()}-${basename(originalname)}`, swallows upload errors and returns `null` rather than throwing, and `getSignedUrl` produces a time-limited `GetObjectCommand` presigned URL (default 3600s) — objects are private by default, read access is always through a signed URL, never a public bucket URL.
- No delete-object, no presigned **upload** URL, no MIME/size validation is implemented yet (multer accepts anything, unbounded).

## 6. Existing API patterns

- Base path `/api/auth`, resource-scoped router per feature.
- Verbs: everything is `POST` (register/login/logout/forgot-password/reset-password/verify-email) — no `GET`/`PUT`/`PATCH`/`DELETE` resource CRUD exists yet to establish a convention there.
- Response shape is **not fully consistent**: success responses are ad hoc (`{ message, user }`, `{ message, user, verificationLink }`), while the centralized `errorHandler` always emits `{ error: { message, status } }`. There is no shared "envelope" helper for success responses — this is a gap the template library should close without inventing something foreign to the rest of the style (plain JSON, `message` as the primary human-readable field, no HAL/JSON:API).
- Status codes via a shared `HttpStatusCodes` enum (`utils/helpers.ts`) rather than magic numbers.
- Auth: JWT access token (15 min expiry, `{ sub, role, type: 'access' }`) set as an `httpOnly`, `sameSite: lax`, `secure`-in-prod cookie, **or** accepted via `Authorization: Bearer`. No refresh token is implemented despite the README mentioning one.
- Errors thrown as `APIError extends Error` with a `.status`, caught by a single `errorHandler` middleware mounted last. Repositories also expose a `handleError(res, error)` helper used inside `catch` blocks in services — two error-handling idioms coexist (throw `APIError` + centralized handler, vs. inline `repository.handleError`).
- Timing-safe patterns already present: `forgotPassword` always returns the same message whether or not the account exists (no user enumeration); reset/verify tokens are single-use (`consumedAt`) and stored hashed.

## 7. Existing conventions worth preserving

- Layered `route → service → repository`, one class per aggregate, PascalCase class names matching the file.
- Centralized `SECRETS` object in `utils/helpers.ts` that validates required env vars **at import time** (fail fast on boot) and casts/defaults numeric and enum-like vars.
- `HttpStatusCodes` enum instead of raw numbers, imported everywhere.
- DTO interfaces in `utils/types.ts`, one file, not colocated per feature.
- bcrypt for password hashing with a configurable, floor-enforced `SALT_ROUNDS` (≥10).
- Secrets/PII-safe tokens: verification/reset tokens generated with `crypto.randomBytes`, only their SHA-256 hash persisted.
- `.env.local` loaded before `.env` (`dotenv` `config({ path: '.env.local' })` then `config()`), so `.env.local` wins for local overrides.
- S3 keys namespaced under a prefix (`uploads/`) with a random UUID to avoid collisions and enumeration.

## 8. Problems / limitations in the reference project (gaps the templates must fill, not blindly copy)

- No controller layer — services are coupled to Express `Request`/`Response`, which makes them hard to reuse outside HTTP (e.g., from a queue worker) and hard to unit test without mocking Express objects. The templates introduce a thin controller boundary so services can take/return plain data.
- Inconsistent success-response envelope (no shared `sendSuccess`-style helper, unlike the consistent error envelope).
- No request-body validation layer beyond hand-rolled checks in `AuthenticationRepository.validateUserData` — not reusable for future resources.
- No RBAC/authorization layer beyond a `role` field that nothing yet checks.
- No pagination/filtering/sorting convention.
- No tests, no CI, no Dockerfile.
- `FileUpload.uploadFileToS3` swallows errors and returns `null` instead of throwing/propagating — inconsistent with the rest of the app's throw-and-centralize pattern.
- No file-type/size validation on upload.
- README promises a refresh token that isn't implemented.
- Two competing error-handling idioms (`throw APIError` vs. `repository.handleError(res, err)`).

## 9. Recommended template abstraction

Preserve: layered architecture, `SECRETS`-style fail-fast env validation, `HttpStatusCodes` enum, hashed/single-use tokens, private-bucket + presigned-URL storage model, transaction-wrapped multi-table writes, dotenv-local-then-default loading.

Add (clearly new, justified by reusability needs the single-feature reference app never had to face): a thin controller layer, a shared success-response envelope, a schema-based request-validation middleware (Zod — same "fail fast, typed" spirit as `SECRETS`), a pagination/filtering/sorting query contract for list endpoints, an RBAC middleware built on the existing `req.user.role`, and a single consistent error-throwing convention (`APIError` everywhere, retire the inline `repository.handleError` idiom for new code).

## 10. Proposed graph architecture

Nodes are organized by category (project, backend, database, storage, authentication, authorization, api, testing, devops, ai, documentation, frontend). Each node is self-contained (`template.yaml`, input/output JSON Schemas, `files/`, `prompts/`, `tests/`, `examples/`) so an orchestration agent can select, configure, and compose them without reading implementation code first. See `graph-templates/GRAPH-NODE-SPEC.md`.

## 11. Proposed template directory structure

See `graph-templates/README.md` §Directory Structure — implemented categories: `project`, `backend`, `database`, `storage`, `authentication`, `authorization`, `api`, `testing`, `devops`, `ai`, `documentation`, `frontend` (partial — see below). `jobs`, `integrations`, `observability` remain entirely `planned` (see `graph-templates/TEMPLATE-REGISTRY.md`).

`frontend` has no reference-app precedent — the reference application ships no frontend at all — so it is not a port of existing code. The implemented Next.js path consists of `project.nextjs` (App Router scaffold), `frontend.nextjs` (typed `apiFetch` client matching the backend response/error envelopes), `frontend.authentication` (session context and login/register using `authentication.password`'s `GET /api/auth/me`), `frontend.forms`, `frontend.tables`, and `frontend.dashboards` (a reusable component, not an application route or backend authorization policy). Those nodes were designed around the existing backend conventions.

The separate implemented Vite path is `project.vite-react` plus `frontend.react`. It reuses the same audited API-client source without Next.js routing or server rendering. Authentication pages, forms, tables, and dashboards still require exact Next.js graph prerequisites; no Vite variants or application page routes are supplied. Both paths need application-specific integration and review before deployment.
