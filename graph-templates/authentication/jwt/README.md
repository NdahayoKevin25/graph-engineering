# authentication.jwt

The engine now provides an audited deterministic JWT renderer. Its
credential, identity, cookie, concurrency and authorization contract is documented
in [the executable authentication guide](../../../docs/authentication-runtime.md).
That runtime emits reviewed source and tests; it does not execute the historical
prompt/asset snippets below, configure secrets, deliver email, or authorize a
deployment automatically. Existing custom code requires explicit reconciliation.

**What.** `generateAccessToken`/`generateRefreshToken`/`hashToken` (`src/utils/tokens.ts`), `authMiddleware` (`src/middlewares/authMiddleware.ts`), and `POST /api/auth/refresh` (`src/routes/authRefreshRoutes.ts`, mounted at `/api/auth`). Access tokens are short-lived, stateless JWTs (`{ sub, role, type: 'access' }`). Refresh tokens are **not** JWTs — they're opaque random values (`crypto.randomBytes(32)`), only their SHA-256 hash persisted in a new `refresh_tokens` table, the same hash-once idiom the reference app already uses for its `auth_tokens` (email verification / password reset) table.

**When.** After `database.neon-postgres.connection` (owns `schema.ts`, which this node appends `refreshTokenTable` to), `backend.error-handler`, `backend.middleware`. Before `authentication.password` (calls `generateAccessToken`/`generateRefreshToken` and persists the refresh token on login) and `authorization.rbac`/`authorization.tenant-isolation` (read `req.user`).

**Requires.** `database.neon-postgres.connection`, `backend.error-handler`, `backend.middleware`.

**Configure via.** `accessTokenTtl` (default `15m`), `refreshTokenTtlDays` (default `30`).

**Produces.** The three files above, plus `refresh_tokens` appended to `schema.ts`; adds `ACCESS_TOKEN_SECRET` to `SECRETS` (only one secret — see Security).

**Connects to.** Downstream: `authentication.password`, `backend.express`, `authorization.rbac`, `authorization.tenant-isolation`.

**Test.** `npm test -- authMiddleware` — verifies a valid access token sets `req.user`, an expired/malformed one is rejected, and a `type: 'refresh'`-shaped payload is never accepted as an access token.

**Why access and refresh tokens use different mechanisms.** Access tokens are stateless JWTs — cheap to verify (no DB hit), but *not revocable* before they expire in isolation (there is no server-side kill switch short of rotating `ACCESS_TOKEN_SECRET`, which invalidates every session at once). Keeping `accessTokenTtl` short (15m default) bounds the blast radius of a leaked one. Refresh tokens are the revocable half: opaque, hashed, DB-backed, with a `revokedAt` column — `POST /api/auth/refresh` rotates them on every use (revokes the presented one, issues + persists a new one), so a stolen-but-already-used refresh token is a dead end, and a single session can be individually killed (e.g. by `authentication.password`'s `logout`) without touching any other session's tokens.

**`authMiddleware` is stateless as generated by this node alone** — it only verifies the JWT signature/claims and trusts the payload, with no DB round-trip (this node has no user table to query yet; it only requires `database.neon-postgres.connection`, not any specific user schema). **`authentication.password` upgrades it** (via a `files.modify` `replace-method` once the `users` table exists): the upgraded version re-loads the user by id on every request and rejects if they were deleted or their `status` is no longer `active` — giving you real instant-revocation-by-suspension, matching the reference app's original `authMiddleware.ts` behavior, at the cost of one DB lookup per authenticated request. If you use `authentication.jwt` without `authentication.password` (e.g. with a different user-storage node), you inherit the stateless (no revocation) version unless you apply an equivalent upgrade yourself.

**Security.** `POST /api/auth/refresh` re-verifies the presented token's hash against the stored row and checks both `revokedAt` and `expiresAt` before issuing anything new — a stolen-but-expired-or-revoked refresh token must fail closed. Both `access_token` and `refresh_token` cookies are `httpOnly`, `sameSite: 'lax'`, and `secure` in production — never expose either to client-side JavaScript or return them in a JSON body.
